# BlueFS(旧 H3 / N3)再评估(M17/F3)

> 2026-08-27。归档已随 M16 交付,本页把设备内元数据与归档脱钩,确认
> **方案 C 维持常态**,N3 门槛改写。本里程碑 **不开工** C++ shim。

## 结论

| 项 | 裁决 |
| --- | --- |
| 方案 C(同盘 meta-dir / 布局 v3 元数据分区) | **常态**(已交付;抽盘演练 N4-1 通过) |
| BlueFS 路线 B2(设备内 mini-FS + rocksdb 自定义 Env) | **持有**,不进 M17–M19 |
| 与归档的关系 | **脱钩**。归档 = zstd 存储类 + Restore(ADR-19),不依赖设备内 FS |
| 本里程碑工程 | 不写 C++ `rocksdb::Env` shim、不 bindgen、不改热路径 |

ADR-16 spike 仍然成立:挂载点可行,但必须 C++ shim + bindgen(约 40 个
虚方法),预算 5~7 pw。没有新的实测否定 spike,也没有新的用户把「无根
分区裸盘」写成合同条款。

## N3 立项门槛(仅此两条,或关系)

同时满足「有人愿意付这 5~7 pw」之前,下列 **至少一条** 为真才拆实现任务
并补 ADR:

1. **裸盘无根分区可挂**:生产形态是整盘交给 FastS3、主机没有(或不允许)
   给 rocksdb 留 POSIX 目录;方案 C 的 meta-dir 无法落地。
2. **元数据 I/O 成为瓶颈**:在目标硬件上测得 rocksdb 所在文件系统
   (日志/页缓存/双缓冲)把前台 PUT/List p99 打到不可接受,且排除了组提交
   窗口、检查点、压缩竞态等已修项。

不再作为门槛的旧挂钩:

- ~~归档/冷数据容量~~(M16 已用压缩档交付)
- ~~「边缘单盘整体迁移」~~(方案 C 同目录 meta + 镜像已满足)

## 方案 C 局限(文档化,可接受)

1. 元数据仍走 OS 文件系统,少一层 FS 日志的理论收益未拿到。
2. 掉盘时元数据与数据同命运(与「抽盘即迁移」一致,视为特性)。
3. 需要一块可写 POSIX 目录(根分区、专用小盘或与镜像同目录)。

证据:DESIGN.md ADR-15 DM5 / ADR-16;layout v3 `metadata_offset`;
`fasts3 init` 默认同盘 meta-dir。
