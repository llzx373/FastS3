# ADR-9:打包 extent 与惰性压缩(小对象空间利用率方案)

> 状态:**已实现(Tier 1 + Tier 2 核心;2026-08-21)**
> 实现取舍:按实施要求**放弃旧布局前置兼容**——布局版本升为 2,旧设备直接拒绝;
> §9 兼容表中的"新二进制读旧设备 / 混合模式 / 回滚"不适用(无双兼容解码、
> 无特性位门控写入、无 legacy 在线迁移)。其余设计(§2~§8、§10 门禁)按文实现。
> 关联:ADR-4(分配器与元数据同事务)、ADR-5(检查点/重放/可达性重建)、ADR-8(rocksdb backstore)、DESIGN §4
> 范围:本 ADR 只定义存储引擎侧的改动;S3 协议层零改动。

---

## 1. 背景与动机

### 1.1 问题:对象级 extent 独占

当前实现中,一个 extent(默认 4MiB)在写入时被**独占分配给单个对象**:

- `ExtentWriter::feed` 每次经 `alloc.allocate(1)` 申请全新 extent,`finalize_extent` 返回的 `ExtentRef` 恒为 `{extent_id, offset: 0, len: st.written}`(crates/fs3-engine/src/lib.rs `ExtentWriter` 实现,§2.2)——对象从 extent 数据区开头写起,写多少算多少,剩余空间**没有任何对象可以复用**;
- 位图 1 bit / extent、引用计数按 extent 记、COW/删除/重放全部按 extent 粒度(ADR-5)——这是"恢复与引用计数极简"的刻意取舍,代价是最小分配单位 = 4MiB;
- 内联阈值 32KiB(`SMALL_OBJECT_LIMIT`),只救 ≤ 32KiB 对象。

### 1.2 现状利用率(实测代码语义计算)

extent 总大小 4MiB = 4,194,304B,含 4KiB 头 → 数据区容量 = 4,190,208B = **恰好 1023 个 4KiB 页**。

| 对象尺寸 | 现状利用率 | 说明 |
| --- | --- | --- |
| ≤ 32KiB | 100% | 元数据内联,零设备 I/O |
| 64KiB | **1.56%** | 独占 4MiB extent |
| 512KiB | 12.5% | 独占 4MiB extent |
| 1MiB | **25.0%** | 独占 4MiB extent |
| 3.9MiB | ~99.9% | 恰好贴满(仍浪费 4KiB 头之外的空间) |
| 5MiB | 62.5% | 4MiB 整 + 第二个 extent 只用 1MiB,剩余 3MiB 浪费 |

**"大量 1MB 左右文件"正是最差区间:默认配置下设备被放大 4 倍使用。** 且"恰好 1MiB"这类常见尺寸,因数据区容量不是 1MiB 整数倍(1023 页),即使调 `--extent-size 1MiB` 也会溢出到第二个 extent(≈50%)。

### 1.3 目标与非目标

**目标:**
- 设备容量内打包 32KiB ~ 4MiB 的多个对象,利用率 ≥ 99%(任意对象尺寸);
- 崩溃一致性模型与现状逐项等价(已应答不撕裂、未应答不可见、账目收敛);
- 恢复协议、检查点格式、位图语义、S3 层**零破坏**;
- 压缩(GC)永远让位于前台请求,任何时刻可暂停/中断/放弃,仅影响空间收敛速度。

**非目标(V1):**
- 跨节点/分布式(不变);
- 碎片整理之外的空间均衡、冷热分层、压缩算法;
- 改变 S3 语义、内联阈值行为、多设备条带化语义。

## 2. 术语

| 术语 | 含义 |
| --- | --- |
| 段(segment) | extent 数据区内一段 4KiB 对齐的连续区间,是对象→设备引用的基本单位(替代"整 extent 引用") |
| 开放 extent | 当前正在被追加写入的 extent(每引擎/未来每核一个),由 watermark 标记已写水位 |
| 封口(seal) | 开放 extent 停止追加,写 extent 头,状态变为 sealed;封口后不可再写 |
| watermark | 开放 extent 已写字节水位(追加位置);可领先于活段最大 end(失败写入孤儿区不回退,以免覆写已提交打包段);恢复时按活段 max_end 重建 |
| 死段/活段 | 被对象元数据可达引用 = 活段;已删除/未提交 = 死段 |
| 打包 extent | 内含 ≥ 2 个对象段(或 1 个对象 + 剩余空间)的 extent,头带 packed 标志 |
| 独占 extent | 整个数据区只属于一个对象的 extent(大对象整块),走既有头 CRC 路径 |
| live_bytes | 每 extent 的活字节数(派生状态,见 D3) |

## 3. 关键设计决策

### D1:变长 4KiB 对齐段,而非固定 64KiB slot

- 段 = 4KiB 对齐的变长区间,对象写多少占多少(≥ 4KiB,按 O_DIRECT 对齐);
- 固定 slot(64KiB)的空闲追踪虽简单,但每对象平均浪费 32KiB(1MiB 对象 ~3%);变长段无洞复用需求时,空闲追踪只需一个 watermark,**浪费 ≤ 4KiB/对象(0.1%)**;
- 段结构与现有 `ExtentRef {extent_id, offset, len}` 同构,只是 offset 语义化(不再恒为 0)。

### D2:段可跨 extent 续写(尾部 spill)——利用率修正的关键

对象在开放 extent 剩余空间不足时,**尾部继续写入新 extent**(对象段列表多一个跨边界段),而非"整对象换新 extent":

- 纯 1MiB 负载:每 extent 1023 页,3 个整对象占 768 页,剩余 255 页不足以放下第 4 个 1MiB 对象 → **若封口丢弃,利用率仅 75%**;允许 spill 后,255 页装入第 4 个对象的前 255 页,剩余 1 页续写到新 extent → **利用率 ≈ 100%**(任意对象尺寸);
- 现状 `ExtentWriter` 已实现跨 extent 切分(大对象多 extent),机制现成,只是要允许"对象尾部跨边界";
- 代价:每个跨边界对象多 1 个段条目(1MiB 对象约每 4 个多 1 条,元数据可忽略);读路径多一段拼接(多段读已有现成循环)。

> 数字核对:4MiB − 4KiB 头 = 4,190,208B = 1023 × 4KiB,恰非 1MiB 整数倍;1MiB = 256 页。spill 后每 extent 数据区全满,设备级利用率 = 1023/1024 ≈ 99.9%(仅剩每 extent 4KiB 头,摊薄 0.1%)。

### D3:段级状态全部派生,零新增持久化账本

**位图(1 bit/extent)、检查点、`a:` 记录保持 extent 级,格式与语义完全不变:**

| 状态 | 是否持久化 | 重建方式 |
| --- | --- | --- |
| extent 位图 | 检查点 + `a:` 记录(不变) | 既有重放(不变) |
| extent 分配记录 | `a:` 记录(不变):**首段分配时发 alloc,末段消亡时发 ref_dec** | 既有重放(不变) |
| live_bytes / 段引用计数 / watermark | **否** | 既有元数据可达性扫描重建(ADR-5 mark 阶段;启动恢复第 4 步已在做全量扫描,见 crates/fs3-engine/src/lib.rs `rebuild_segment_state`) |
| 共享段稀疏表(COW) | 否 | 同上 |

推论:
- 恢复协议 = 检查点 + `a:` 重放 + 可达性扫描,与现状**步骤一一对应**,只是第 4 步的"引用计数"下沉为"段级引用计数 + live_bytes + watermark";
- 不存在"段账本与元数据两本账对不上"的问题——段状态不是账本,是元数据的投影;
- 启动不做额外全量扫描(现状已做),分阶段启动(见 5.7)仅为可选优化。

### D4:分层落地

| 层 | 内容 | 必要性 |
| --- | --- | --- |
| Tier 1 | 追加式打包(本 ADR §5) | 根治利用率问题,必须 |
| Tier 2 | extent 级惰性压缩(§6) | 高删除/覆盖率负载的空间收敛,强烈建议 |
| Tier 3 | 原地洞复用(§7) | 碎片极端场景,可选 |

Tier 1 不依赖 Tier 2 即可正确运行(Tier 2 只影响空间收敛速度);Tier 3 完全独立。

## 4. 数据模型与磁盘格式

### 4.1 段(Segment)

```rust
/// 对象 → 设备的引用单位(替代现有 ExtentRef;offset 语义化)
struct Segment {
    extent_id: u32,
    offset: u32,   // extent 数据区内偏移,4KiB 对齐(打包段可为任意对齐值;独占段恒为 0)
    len: u32,      // 4KiB 倍数
    crcs: Vec<u32>, // 仅打包段:段内 64KiB 网格 CRC(≤ 64 项 = 256B);独占段为空
}
```

- 对象元数据 `ObjectMeta.extents: Vec<Segment>`;`inline` 字段不变;
- 元数据值格式加版本字节(postcard 编码,键布局不变);旧值(无版本字节/legacy)按"全独占段"解码,读路径双兼容;
- 跨 extent 对象:独占段(整块,头 CRC)+ 可选打包尾段(元数据 CRC),见 4.3。

### 4.2 extent 头改造

```
现:magic | 代数 | owner_id | object_offset | chunk_size | chunk 数 | CRC32C[64] | 头 CRC | 预留
改:magic | 代数 | flags(bit0=packed) | 预留(owner_id/object_offset 弃用归零) | chunk_size | chunk 数(=0) | 头 CRC | 预留
```

- **打包 extent 头不再存 CRC 表**(chunk 网格随段存元数据);独占 extent 头保持现状(CRC 表),大对象读路径零改动;
- **头延迟到封口时写**(数据之后写,防撕裂);崩溃导致头缺失的 extent 由可达性扫描判为孤儿回收,或由 `check` 补写头(读路径不依赖头,见 5.3);
- 代数语义不变(释放时 +1,防陈旧头误判)。

### 4.3 CRC 混合放置

| 段类型 | CRC 存储 | 校验来源 | 读路径改动 |
| --- | --- | --- | --- |
| 独占段(整 extent 属于一个对象) | extent 头 CRC 表(现状) | 头 | 无 |
| 打包段(≤ 4MiB) | 对象元数据 `Segment.crcs`(段内 64KiB 网格,≤ 256B) | 元数据 | 仅 verify_reads 分支 |

- 写路径 CRC 数学不变(按写流 64KiB 累积,尾部按实际数据 CRC、补零落盘)——与现状逐字节一致,只是打包段的表存放位置不同;
- 大对象 = N 个独占段(头 CRC)+ 1 个打包尾段(元数据 CRC),两来源按段拼接校验;
- 无读改写:写路径从不读旧数据。

### 4.4 分配器内存态(新增/变更)

```rust
struct Allocator {
    bitmap: Bitmap,                 // 不变(1 bit / extent)
    live_bytes: Vec<AtomicU32>,     // 新增:每 extent 活字节数(64TiB/4MiB = 16M extent × 4B = 64MiB)
    state: Vec<AtomicU8>,           // 新增:Free | Open | Sealed(启动重建)
    shared: Mutex<HashMap<(u32,u32,u32), u32>>, // 新增:稀疏共享段引用计数(仅 COW 共享段,默认 1 不占条目)
    // 既有:refcounts(extent 级,降级为位图辅助)/ generations / staged / 统计
}
struct OpenExtent { extent_id: u32, watermark: u32, chunk_crcs: Vec<u32> }  // 每引擎(未来每核)一个
```

- 运行时新增内存:live_bytes 数组(与 extent 数线性,64MiB @ 64TiB)+ 稀疏共享段表(与"被 COW 复制的段数"线性,通常极小);
- **不需要**"全量段清单"常驻内存——删除/覆盖时按对象自己的段列表递减即可,只有 Tier 2 发现/校验才临时构建(§6.2)。

### 4.5 `a:` 记录语义(格式不变,触发时机变化)

| 记录 | 现状触发 | 新触发 |
| --- | --- | --- |
| `alloc(extent)` | 每对象申请 | **该 extent 首段被分配**(开放 extent 首次使用) |
| `ref_dec(extent)` | 引用计数归零 | **live_bytes 归零**(末段消亡) |
| `ref_inc(extent)` | COW | 不再使用(段级共享不改变 extent 位图;仅内存稀疏表) |

- 位图权威性不变:检查点 + `a:` 重放仍精确恢复位图;
- 中间态(某 extent 有活段但位图已置位)天然由"首段事务"覆盖,无需逐段记录;
- `staged` 回滚需扩展:live_bytes 递减/清零的暂存与回滚(仿照现有 `cleared` 列表)。

### 4.6 超块特性位与布局版本

- 超块新增特性位 `PACKED_EXTENTS(0x2)` + 布局版本 +1;
- **读路径无条件兼容两种 extent(按头 flags 分支)**,特性位只门控"新写入是否打包"(配置 `storage.packing = true|false`,默认 true);
- 旧设备不迁移即可被新二进制打开:旧 extent 按独占读,新写入按打包写(混合模式);回滚同理(关特性位,打包 extent 仍可读)——**零数据搬迁的兼容/回滚**。

## 5. Tier 1:追加式打包

### 5.1 写路径

```
PUT 数据流(每对象一个 ExtentWriter,共享本引擎的开放 extent):
  开放 extent 不存在或已封口
    → alloc.allocate(1) 申请新 extent(首段事务发 alloc 记录)
    → 若该 id 在对象/分片快照仍有活段(live_bytes 误归零后重分配)
      → watermark = align_up(活段 max_end),不得从 0 覆写;已写满则封口换 id
    → 否则初始化为 Open{watermark: 0}
  当前段 = 从 watermark 起写(4KiB 对齐):
    够装 → 整段写入,watermark += len,对象段列表追加 {E, old_watermark, len}
    不够装 → 写满当前 extent(watermark = 容量)封口;申请新 extent,
             剩余部分续写(跨边界尾段,D2);watermark 继续推进
  对象写完 → 元数据事务(对象 + 首段 alloc 记录[如新 extent] + 段 CRC 表)→ 组提交
  封口判定(任一):
    a) watermark == 容量(写满)
    b) 剩余空间 < 32KiB(剩余空间装不下任何非内联对象;> 32KiB 的才走设备)
    c) 内部出现死段(seal-on-delete,5.4)
```

要点:

- **writer 跨对象存活**是核心重构:现状 `ExtentWriter` 每对象一个、extent 随对象消亡;改造后"extent 会话"跨对象,每对象复用同一 watermark 推进逻辑(代码改动集中在 `ExtentWriter` 生命周期 + `finalize_extent` 拆分出"段引用"与"封口");
- 首段 alloc 记录随首段所属对象的元数据事务提交;若该事务失败,内存位图经既有 staged 回滚——与现状"写入中断释放 extent"一致;**开放 extent 水位不回退**(孤儿区由后续追加跳过,恢复按活段 max_end 覆盖)。回退陈旧水位会覆写已提交打包段。
- 大对象自动收益:3.9MiB 对象写满 extent 后自然续接,其尾段剩余空间由后续对象填充,**"大对象尾浪费"问题顺带消除**;
- 并发:现状 service 层 engine 写锁串行写路径,开放 extent 天然单写者;M5 thread-per-core 后每核引擎实例各持一个开放 extent,互不干扰。

### 5.2 封口类型判定(独占 vs 打包)

封口时按"本 extent 数据区参与对象数"定类型:

- 仅 1 个对象且写满(大对象整块)→ **独占 extent**:头写完整 CRC 表,读路径走既有头校验,零改动;
- 其余(≥ 2 对象,或 1 对象未写满)→ **打包 extent**:头写 packed 标志 + 空 CRC 表;各段 CRC 在各自元数据。

由此,大对象(> 4MiB)的主路径完全保持现状(独占段 + 头 CRC + sendfile/splice 零拷贝),打包只影响 32KiB ~ 4MiB 区间与跨界尾段。

### 5.3 读路径(零改动 + verify 双来源)

- 普通读(`verify_reads=false`):按 `Segment` 列表逐段定位设备偏移,与现状多 extent 拼接循环一致,`sendfile/splice` 每段一次——**零改动**;
- `verify_reads=true`:逐段校验——独占段读 extent 头 CRC 表(现状),打包段读 `Segment.crcs`(元数据);唯一改动点;
- 条件头/Range 裁剪逻辑不变(段级拼接前裁剪)。

### 5.4 删除 / 覆盖

```
删除对象 → 按段列表逐段:
  live_bytes[E] -= len
  若 E 是开放 extent → 封口(seal-on-delete 策略,见下)
  若 live_bytes[E] == 0 → 位图清位 + 代数+1 + ref_dec 记录(同事务)
覆盖 = 新段分配 + 旧段释放,同一事务(现状语义不变)
```

**seal-on-delete 策略**:开放 extent 内部一旦出现死段即封口。理由:保持"开放 extent 无洞"(watermark == 活段最大 end),追加永远顺序;洞只出现在 sealed extent,由 Tier 2 统一处理。这是策略而非正确性要求(不封口也安全,只是 Tier 2 候选变多),实现为一个比较 + 封口调用。

### 5.5 COW 复制(CopyObject)

- 新对象元数据直接引用原对象的段列表(段级共享,零数据 I/O);
- 共享段进稀疏表 `shared[(extent, off, len)] += 1`;段被复制后,原段引用计数 > 1;
- 删除/覆盖共享段:计数 -1,归零出表并递减 live_bytes——**COW 粒度从 extent 下沉到段**:复制一个 1MiB 打包对象只共享它的 1MiB 段,不再独占整个 4MiB extent(顺带修复现状"COW 使小对象复制浪费整个 extent"的问题);
- 位图/a: 记录不受影响(段共享不改变 extent 分配状态)。

### 5.6 检查点(不变)

位图 + 统计(extent 级)双缓冲、30s / 64MB 增量、槽代数/CRC——**全部不变**;live_bytes 等段状态不进检查点(D3)。

### 5.7 恢复协议(与现状逐步骤对应)

```
1. 读超块(校验 CRC/布局版本;特性位不阻断)
2. 打开 rocksdb(WAL 恢复)
3. 加载检查点位图 + 重放 seq 后 a: 记录 → 位图(不变)
4. 元数据可达性扫描(mark):
   - 段级引用计数(共享段 → 稀疏表)
   - live_bytes[E] = Σ 活段 len;归零且位图置位 → 泄漏,回收
   - watermark(开放 extent)= 该 extent 活段最大 end(跨崩溃会话的孤儿区
     [旧 watermark, 旧 written_end) 无活段 → 新追加自然覆盖,无残留风险;
     进程内 abort 同样不把水位退回陈旧 committed_end)
5. (后台)泄漏扫描复核 / 开放服务
```

- 现状第 4 步已是全量可达性扫描(ADR-5;`rebuild_segment_state`),段状态只是同一遍扫描的副产品——**不新增启动阶段**;
- 分阶段启动(可选增强):扫描完成前只允许读 + 新 extent 分配,不允许开放 extent 追加,避免在未收敛 watermark 上写入;默认不启用(扫描与重放一致性由门禁保证)。

### 5.8 崩溃一致性窗口对照(与现状逐项等价)

| 窗口 | 状态 | 恢复动作 | 与现状差异 |
| --- | --- | --- | --- |
| 段数据落盘后、元数据提交前 | 孤儿段 | 扫描判 free | 无(现状孤儿 extent) |
| 元数据提交后(含首段 alloc) | 对象可见、位图已置位 | 正常 | 无 |
| 段 refcount/live_bytes 事务中途崩溃 | rocksdb 原子性 | 重放 + 扫描收敛 | 无 |
| 封口头缺失(未封口崩溃) | 无头、有活段 | 读不依赖头;`check` 可补写头 | 新增,已分析无害 |
| 跨会话覆盖孤儿区 | 旧 CRC 过期 | 新会话重算,封口时写新表 | 无(头在封口时整体写) |

结论:所有窗口的语义与现状一致——**已应答对象永不撕裂、未应答对象不可见、空间账目收敛**;证明方式不变(kill -9 harness)。

## 6. Tier 2:惰性压缩(extent 级)

### 6.1 原则

> **压缩是空间回收加速器,不是正确性组件。** 压缩的任何失败/暂停/中断都只让空间收敛变慢;因此压缩永远让位于前台请求——与 LSM"写压力触发 → write stall"、SeaweedFS"整卷 vacuum"形成对照。

### 6.2 四阶段流水

**阶段 1 发现(零锁):**
- 候选 = sealed 且 `live_bytes < 阈值`(默认 50%)的 extent,**直接读内存 live_bytes 数组,无需扫描**;
- 按 `wasted = 容量 − live_bytes` 排序取 Top-K(默认 K=64)进入本轮;
- 段清单(哪些对象引用候选 extent)构建:一轮**只读快照扫描**(rocksdb snapshot,MVCC,与并发写完全隔离)同时产出全部候选的段清单——`o:` 对象 + `p:` multipart 分片两个前缀都扫;内存上界 = K × 每 extent 最大段数(4MiB/32KiB ≈ 128)× 32B ≈ 256KB,可忽略;
- 不建持久化 `x:` 索引(省掉每对象一个 KV 的元数据开销),代价是发现需一轮快照扫描——压缩频率低,摊销后可忽略。

**阶段 2 拷贝(零锁):**
- 为候选 extent 申请新 extent(压缩 worker 独占),把活段数据**按段顺序拷贝**落盘(数据先行;设备写走 `io` Mutex 短临界区);
- 新 extent 的段此刻是孤儿——扫描本就视孤儿为 free,安全。

**阶段 3 切换(唯一排队点):**
- 每个受影响对象**一条短事务**:`对象元数据段列表更新(旧段→新段)+ 新段 alloc 记录[首段] + 旧段 live_bytes 递减[归零则 ref_dec]`,组提交批量;
- **快照隔离 + 乐观重试**:迁移基于阶段 1 快照;提交时读集校验,对象被并发覆盖/删除 → **放弃该对象,下轮再来**(abort-and-retry-later,永不饥饿任何人,因为压缩没有截止时间);
- **恒为单对象事务**:不跨对象原子性要求;共享段策略见 6.5。

**阶段 4 释放(派生状态):**
- 旧 extent 的 `live_bytes` 随每个切换事务递减,归零 → 位图清位 + ref_dec 记录(同事务);
- 崩溃恢复:新段孤儿回收、旧段原样保留、live_bytes 由扫描重建——**没有"切换与释放必须原子"的硬约束**,释放是可重放收敛的派生账目。

### 6.3 锁域分解(压缩 worker 不拿引擎大锁)

代码现状支持压缩 worker 做成独立组件,仅通过公开接口操作:

| 资源 | 现状 | 压缩 worker 交互 |
| --- | --- | --- |
| 引擎大锁 `Arc<RwLock<Engine>>`(service 层) | 写路径串行 | **不获取**(不调用 engine 的 put/delete 等高层方法) |
| `meta`(rocksdb) | `commit(&self)`,内部并发安全(fs3-meta `MetaStore::commit`) | 直接发起迁移事务 |
| `alloc` | 内部 `Mutex<Staged>`(fs3-alloc/src/lib.rs:39) | 短暂临界区(allocate/release/rollback) |
| 设备 IO | `Mutex<Box<dyn IoEngine>>`(fs3-engine/src/lib.rs:99) | 拷贝时短临界 |

- 前台读路径(读锁)与压缩**零互斥**;
- 前台写路径与压缩的互斥只剩"在 rocksdb 乐观事务 `s:seq` 串行点各排一次队"——这本就是所有事务的常态机制,压缩通过节流控制插入频率(6.4);
- 前提:迁移事务只触碰 `meta + alloc + io`,不触碰 engine 的 checkpoint 计时等状态(压缩不触发检查点增量统计的 alloc_since?——新 extent 分配计入统计,设计上允许,见 6.4 节流;实现时把压缩的 alloc 单独计数或合并均可,文档明示即可)。

### 6.4 节流与背压

> **实现状态(REVIEW §3.8 同步)**:全局速率上限、容量水位提升、压缩暂停原语为
> **已实现**;组提交窗口占用率闸门与前台延迟背压为**规划**(依赖 meta 组提交占用率
> 与 p99 延迟信号的跨组件接线,当前未落地,如实标注)。

| 机制 | 默认 | 状态 | 说明 |
| --- | --- | --- | --- |
| 组提交窗口占用率闸门 | 批内 ≤ 25% 为压缩事务 | 规划 | 空闲窗口才插队,前台满时自动退让 |
| 全局速率上限 | 64 MiB/s(可配) | ✅ 已实现 | 拷贝 + 迁移字节计数,`compact_batch` 内预算节流 |
| 前台延迟背压 | PUT/GET p99 超过基线 ×2 暂停 | 规划 | 用既有指标(延迟直方图)驱动,恢复后继续 |
| 容量水位提升 | > 85% 时预算 ×4 | ✅ 已实现 | `live_bytes_total / (extent 数 × capacity) > 85%` 时预算 ×4 |
| 压缩暂停原语 | admin API | ✅ 已实现 | `Engine::set_compaction_paused` + admin repair 入口 |

节流信号全部来自现有指标体系(fsync p99、ring 深度、延迟分位),不新增采集。

### 6.5 共享段策略

- 共享段(refcount > 1)默认**跳过**:留在旧 extent,不阻止其余段迁移;若 extent 只剩共享段,保持候选状态待后续轮次(共享段是活数据,不迁移不构成浪费);
- 可选策略"复制式迁移":为单个引用者复制一份新段(单对象事务即可完成,写放大 = 共享段数 × 段大小,仅建议共享段占比极低时开启);
- 理由:共享段占比低(COW 复制量小),跳过策略让迁移事务恒为单对象、无跨对象原子性。

### 6.6 崩溃/失败语义

| 场景 | 结果 |
| --- | --- |
| 阶段 2 崩溃 | 新段孤儿 → 扫描回收;旧状态完整 |
| 阶段 3 事务失败(冲突) | 放弃该对象;新段孤儿回收(或复用);旧段保留 |
| 阶段 4 崩溃(部分对象已迁) | 已迁对象读新段,未迁读旧段,全部有效;旧 extent 保持分配,下轮继续 |
| 压缩全程被暂停/禁用 | 空间收敛变慢,正确性零影响 |

### 6.7 `check --compact`:在线迁移与离线整理

- 同一套压缩机制,两档运行:
  - **在线**:后台低优先级(上述节流),同时把 legacy 独占小对象段重写为打包段(迁移旧设备数据布局);
  - **离线/低峰**:`fasts3 check --compact` 前台跑,高预算,输出迁移报告;
- 覆盖场景:旧设备升级打包布局、碎片整理、`x:` 未建情况下的定向检查(压缩发现阶段与泄漏扫描共用快照扫描代码)。

### 6.8 与 vacuum / LSM 对比

| 风格 | 冲突来源 | 本方案对照 |
| --- | --- | --- |
| SeaweedFS vacuum(整卷重写) | 与读写共享卷文件;临时双倍空间;I/O 尖峰 | 粒度 = 单 extent(≤4MiB),无临时空间需求(新段逐事务推进),节流 |
| LSM compaction(写压力触发) | 压力越大越压缩 → write stall | 反向:压力越大越暂停(压缩非正确性必需) |

## 8. 空间效率与开销账本

### 8.1 利用率对比(任意对象尺寸,spill 后)

| 对象尺寸 | 现状 | Tier 1 后 | 说明 |
| --- | --- | --- | --- |
| ≤ 32KiB | 100% | 100% | 内联不变 |
| 64KiB | 1.56% | ~99.9% | 打包 |
| 512KiB | 12.5% | ~99.9% | 打包 |
| 1MiB | 25.0% | ~99.9% | 打包 + spill |
| 3.9MiB | ~99.9% | ~99.9% | 打包 + spill |
| 5MiB | 62.5% | ~99.9% | 独占整块 + 打包尾段 |
| 1TiB 大对象 | ~100% | ~100% | 独占段为主,尾段打包 |

设备级上界 = 1023/1024 ≈ 99.9%(每 extent 4KiB 头)。**1TiB 的 1MB 文件:设备占用从 ~4TiB 降到 ~1.001TiB。**

### 8.2 元数据开销

| 项 | 量级 | 说明 |
| --- | --- | --- |
| 段 CRC 表 | ≤ 256B/对象 | 打包段 ≤ 4MiB → ≤ 64 × 4B;独占段为空 |
| 跨边界尾段 | +1 段条目/跨边界对象 | 1MiB 对象约每 4 个 +1 条(~32B) |
| `x:` 索引 | 0 | 已否决(压缩靠快照扫描) |
| 合计 | ~+100~300B/对象 | 1 亿对象级 ≈ +10~30GB,对 LSM 可接受;可选仅元数据值开 zstd |

### 8.3 内存开销

| 项 | 量级 |
| --- | --- |
| live_bytes 数组 | u32 × extent 数(64TiB/4MiB → 64MiB) |
| 稀疏共享段表 | ∝ COW 共享段数(通常极小) |
| 开放 extent | 每引擎 1 个(4KiB 头缓冲 + watermark) |
| 压缩段清单(瞬态) | ≤ 256KB(见 6.2) |

无"全量段清单"常驻,内存与对象数解耦(与现状一致)。

### 8.4 写放大

| 路径 | 写放大 | 说明 |
| --- | --- | --- |
| 前台写入 | 1(Tier 1) | 数据只写一份,无复制/EC(底层 HA) |
| Tier 2 压缩 | 活段重写 ≤ 1(每候选) | 仅重写活段;与 SeaweedFS vacuum 同级但粒度小一个量级 |
| COW 复制 | 0 | 元数据操作(不变) |

## 10. 门禁与测试

### 10.1 单元 / 属性测试

- 段分配器不变量(proptest):段不重叠、watermark 单调、live_bytes == Σ 活段、归零即清位、共享段稀疏表与删除一致;
- spill 正确性:随机对象尺寸(32KiB~8MiB)跨边界切分,读回逐字节一致;纯 1MiB 负载利用率断言 ≥ 99%;
- `a:` 记录触发时机:首段/末段边界(含跨崩溃会话孤儿覆盖、封口后内部删除);
- CRC 双来源:独占段(头)与打包段(元数据)verify_reads 各自与混合拼接校验;
- 封口类型判定:独占/打包/未封口崩溃三种 extent 的读写与 check 行为。

### 10.2 崩溃一致性 harness(扩展现有 tests/crash)

- 随机混合负载:对象 32KiB~8MiB 随机尺寸 + 删除/覆盖/CopyObject/COW 共享段 + 压缩并发(开关随机);
- kill -9 任意时刻 → 重启断言:无撕裂对象(已应答完整、未应答不存在)、`check` 零泄漏零漂移;
- 压缩中断注入:阶段 2/3/4 各窗口崩溃,收敛性断言;
- 轮次:现有 50/100 轮基线提升到 200 轮(段级状态面更大)。

### 10.3 协议与回归

- CEPH s3-tests 全量(M1+M2 107 项)零回归;
- 零拷贝读路径(sendfile/splice)基准零回归(大对象独占段路径未动);
- 内存基线:混载 RSS 增量 ≤ 现状 + live_bytes 数组量级。

### 10.4 性能与空间基准(新增门禁)

- **利用率基准**:1MiB 对象负载,`check` 报告设备占用 / 逻辑字节 ≥ 99%;(现状基线 25%);
- **压缩影响基准**:PUT p99 在压缩开/关两档差异 < 5%(默认预算);压缩暂停/恢复无前台可见尖峰;
- **恢复基准**:段级恢复耗时相对现状 + ≤ 10%(同一遍扫描,仅多算段状态)。
